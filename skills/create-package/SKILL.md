# Create an Invariant package

Scaffold a package — directory structure, item files, and a single `invariant.json`
manifest — then let the CLI generate and validate the manifest.

## Usage

Invoke when a user wants to author, restructure or publish an Invariant package, or
needs the rules behind `invariant.json`, the six item types, or installed naming.

Do not invoke to *use* an already-installed package, or to edit `.agents/`, `.claude/`,
`.cursor/` or `.github/` — those are generated projections, not sources.

## `invariant.json`

One file, three modes, auto-detected by which keys are present.

**Project mode** — consumes packages. This is the file at the root of a repository that
*uses* Invariant.

```json
{
  "name": "my-workspace",
  "version": "1.0.0",
  "targets": ["claude", "codex"],
  "packages": {
    "@acme/dev": { "name": "@acme/dev", "version": "1.2.0",
                   "source": "github", "sourceUrl": "github:acme/dev" }
  },
  "active": [
    { "package": "@acme/dev", "type": "skills", "item": "release-notes" }
  ]
}
```

| Key | Owner | Meaning |
|---|---|---|
| `targets` | you | which assistants get projections — `claude`, `codex`, `cursor`, `copilot`, `aider`, `windsurf` |
| `packages` | CLI (`invariant install`) | resolved package name, version, and where it came from |
| `active` | CLI (`invariant add` / `remove`) | the items actually installed. `item` is the item's **own** name; the installed name is always derived, never stored |

**Package mode** — publishable. This is the file at the root of a repository that *is* a
package. Presence of `items` is what marks it publishable.

```json
{
  "name": "@acme/dev",
  "version": "1.2.0",
  "description": "Release tooling and conventions for Acme services.",
  "author": "acme",
  "license": "MIT",
  "repository": "https://github.com/acme/dev",
  "items": {
    "skills": [{ "name": "release-notes", "description": "Generates a CHANGELOG entry." }],
    "rules":  [{ "name": "layer-deps",   "description": "Enforces dependency direction." }]
  }
}
```

| Field | Required | Owner | Notes |
|---|---|---|---|
| `name` | yes | you | the `invariant install <name>` id; lowercase, hyphens, optional `@scope/` |
| `version` | yes | you | semver `major.minor.patch` |
| `description` | recommended | you | registry / search copy |
| `author`, `license`, `repository` | no | you | metadata |
| `items` | yes to publish | **CLI** | `type → [{name, description}]`. Generated by `invariant package create` / `refresh`. Never hand-maintain it |

Only `name` and `version` are enforced by the CLI; `description`, `author`, `license`
and `repository` are this package's recommended minimum, not schema requirements.

**Hybrid mode** — both key sets in one file: a repository that publishes a package and
also consumes others. Nothing special is declared; the CLI detects it.

```json
{
  "name": "@acme/dev",
  "version": "1.2.0",
  "targets": ["claude"],
  "packages": { "@invariant-guru/cli": { "name": "@invariant-guru/cli", "version": "1.3.0",
                "source": "github", "sourceUrl": "github:invariant-guru/skills-invariant" } },
  "active": [{ "package": "@invariant-guru/cli", "type": "skills", "item": "create-package" }],
  "items": { "skills": [{ "name": "release-notes", "description": "Generates a CHANGELOG entry." }] }
}
```

`invariant-package.json` is a legacy filename from older versions. If a repository still
has one, leave it in place and add `invariant.json`; there is no migration command and
deleting it is the owner's call.

## Authored tree vs generated tree

You author the left side. The CLI owns the right side.

```
acme-dev/                        # ← yours, committed
├── invariant.json               #   metadata yours, `items` block the CLI's
├── README.md                    #   required at the package root
├── agents/reviewer.md
├── skills/release-notes/SKILL.md
├── commands/scaffold.md
├── rules/layer-deps.md
├── contexts/stack.md
└── instructions/onboarding.md

consumer-repo/                   # ← generated by `invariant sync`, gitignored
├── .agents/<type>/<qualified>   #   canonical store
├── .claude/<type>/<qualified>   #   symlinks into .agents/
├── .cursor/rules/<qualified>.mdc
├── .github/instructions/<qualified>.instructions.md
└── .invariant/
    ├── cache/<package>@<version>/…
    ├── contexts/<package>/<name>.md
    └── instructions/<package>/<name>.md
```

Never author into or commit the generated side — `invariant sync` rebuilds it. But
"generated" applies only to the paths Invariant manages: a hand-written
`.claude/settings.json` or an unrelated `.github/workflows/` file is not disposable.
`invariant sync --check` reports drift without writing; `--force` replaces target files
that were hand-edited away from the canonical item.

## The CLI

| Command | Does | Writes |
|---|---|---|
| `invariant package create -n <name> --version <v> …` | scans the folder, adds package metadata, fills `items` | `invariant.json` |
| `invariant package refresh` | rescans items and updates `items` | `invariant.json` |
| `invariant package validate` | checks `items` against disk; lints naming | nothing |
| `invariant inspect <pkg> --paths` | prints package, type, installed name, canonical path, tab-separated | nothing |
| `invariant sync` | rebuilds `.agents/` and every target projection | generated tree only |
| `invariant package publish` | validates, bundles, uploads | registry |

## Item types (exactly six)

`agents`, `skills`, `commands`, `rules`, `contexts`, `instructions`.

- **Skills** — always a folder `skills/<name>/` with a required `SKILL.md`; extra `.md`
  files and sub-folders are bundled. Item name = folder name. Never a single file.
- **Every other type** — a single file `<type>/<name>.md` (item name = filename without
  `.md`) or a folder `<type>/<name>/*.md` (item name = folder name, all `.md` bundled).
  Mix freely within a type.
- Only create directories for the types the package actually provides.

Choose by how the content is consumed, not by how much of it there is:

| Need | Type |
|---|---|
| A procedure run on demand, with steps, inputs and outputs | **skill** |
| Knowledge that must be in context on *every* turn | **instruction** (it is folded into the target's context file — expensive, keep it short) |
| Background material the model consults when relevant | **context** |
| A constraint that must always hold | **rule** |
| A behavioural persona for a class of task | **agent** |
| A user-typed `/command` | **command** |

Default to the fewest types that do the job. A package of one good skill beats a package
that ships all six because the template had six slots.

## Installed names

An item does not keep its bare name once installed. The CLI prefixes it with a slug of
the **package** name, so two packages shipping a `frontend` skill cannot overwrite each
other:

```
slug(packageName)    -> drop "@", "/"->"-", lowercase, non-[a-z0-9._-]->"-", collapse "-"
qualified(pkg, item) -> item if item === slug or item starts with slug + "-"
                        otherwise slug + "-" + item
```

`docs` + `frontend` → `docs-frontend`. `@invariant-guru/cli` + `create-package` →
`invariant-guru-cli-create-package`. Pure function, idempotent, computable by hand.

| Location | Prefixed | Path |
|---|---|---|
| Canonical store | yes | `.agents/<type>/<qualified>` (folder) or `.agents/<type>/<qualified>.md` |
| Claude Code | yes | `.claude/<type>/<qualified>` — symlink into `.agents/` |
| Cursor | yes | `.cursor/rules/<qualified>.mdc` |
| Copilot | yes | `.github/instructions/<qualified>.instructions.md` |
| Codex, Aider | inherited | read `.agents/` or embed the content |
| Contexts, instructions | **no** | `.invariant/{contexts,instructions}/<package>/<name>.md`, folded into each target's context file |
| Package cache | **no** | `.invariant/cache/<package>@<version>/<type>/<item>` |
| Your repository | **no** | keep authoring `skills/frontend/` — the prefix is an install-time projection |
| CLI arguments | **no** | `invariant add skill:<package>/<item>` takes the item's own name |

Nothing rewrites content at install time, so **any link to your own item must spell the
prefixed path yourself** — with one exception: files *inside* one skill folder travel
together, so `[skill-authoring.md](references/skill-authoring.md)` stays relative and
correct. Cross-item links do not.

Full algorithm, both authoring strategies, collisions and the pre-prefix upgrade path:
[package-naming.md](references/package-naming.md).

## Procedure

### Step 1 — Gather metadata

Take what the user already said; ask only for what is missing and consequential.

Needed: package **name** (lowercase, hyphens, optional `@scope/`), **description**,
**author**. Defaulted: **license** `MIT`, **version** `1.0.0`, **repository** optional.

### Step 2 — Choose items and compute names

Decide which of the six types the package needs, using the table above, and collect a
name and a one-line description for each. Then, **before authoring any content**, write
down the installed-name map:

```
package @acme/docs  ->  slug acme-docs
  skills/frontend         -> .claude/skills/acme-docs-frontend/SKILL.md
  agents/reviewer         -> .claude/agents/acme-docs-reviewer.md
  instructions/onboarding -> .invariant/instructions/@acme/docs/onboarding.md  (not prefixed)
```

Show the map to the user. Links written from it are right the first time; links patched
afterwards are the usual source of dead paths.

### Step 3 — Scaffold and author

Create the package directory, `README.md`, and each item:

- **Skill** → `skills/<name>/SKILL.md`, plus any `references/`, `scripts/`, `assets/`.
- **Other** → `<type>/<name>.md`, or `<type>/<name>/*.md` for a multi-file item.

Author under the item's **own** name (`skills/frontend/`), unless you deliberately
pre-prefix — safe by idempotence, and worth it when the slug is short, because the
repository layout then matches the installed layout byte-for-byte. Pick one strategy and
apply it to every item in the package.

Before writing a `SKILL.md`, read [skill-authoring.md](references/skill-authoring.md).
The load-bearing parts:

- Frontmatter first line. `name`: ≤64 chars, `[a-z0-9-]` only, and never containing
  `anthropic` or `claude`. `description`: non-empty, ≤1,024 chars, third person, stating
  what it does **and** when to use it, trigger words front-loaded.
- Set `name` to the item's **qualified** name — Claude Code derives the invocation name
  from the installed directory, not from the frontmatter, so the two must agree.
- Body under 500 lines; depth goes into `references/`, one level deep from `SKILL.md`.
- Name the inputs, the output paths, the failure modes and the done condition.

Do not hand-write the `items` block — the CLI generates it next.

### Step 4 — Generate the manifest

From the package root:

```bash
invariant package create \
  --name <name> --version <version> \
  --description "<desc>" --author "<author>" \
  --license MIT --repository "<url>"
```

This scans the folder, writes `invariant.json`, and fills `items` (it refreshes
internally). Re-run `invariant package refresh` after adding or removing item files.

**Two known behaviours to check for afterwards, not to edit around:**

- On a directory whose `invariant.json` has no `items` block yet, `create` may write the
  metadata and then fail with `This directory is not a publishable package. No 'items'
  block in invariant.json. Run 'invariant package create' to promote it.` — the metadata
  *was* written. Re-read the exact message and `invariant package create --help` from the
  installed CLI before doing anything else; if the version in front of you cannot
  bootstrap a manifest, report that to the user rather than hand-writing the `items`
  block. `items` is CLI-owned; hand-editing it hides the failure and drifts silently.
- The manifest description of each item is taken from the item's first file: **first
  non-empty line, leading `#` stripped, YAML frontmatter not skipped.** A `SKILL.md` that
  opens with `---` therefore lands in the manifest as `"description": "---"`. Read
  `invariant.json` after every refresh and restore the real one-line description. Keep the
  frontmatter — it is what the host reads; the manifest string is registry copy.

### Step 5 — Validate

```bash
invariant package validate
```

Reports `missing_on_disk` (declared, absent) and `undeclared_on_disk` (present,
undeclared) — usually fixed by `invariant package refresh`. It also warns
`unprefixed_path_reference` when an item links to `.claude/<type>/<name>` (or `.agents/`,
`.cursor/rules/`, `.github/instructions/`) for one of **your own** items without the
prefix, naming the path that will actually exist. Warnings never make a package invalid,
but each one is a link that 404s after install. Fix them all.

```bash
invariant inspect <package> --paths   # the copy-paste source for correct references
```

### Step 6 — Publish

```bash
invariant package publish
```

Validates, bundles, and uploads. Requires `INVARIANT_TOKEN` or `invariant login`.

Publishing is outward-facing and hard to undo. Run it only when the user has actually
asked for it — a package being ready to publish is not permission to publish it.

## Content guidelines per type

- **Skills** — frontmatter + `## Usage` + ordered `## Procedure`. See
  [skill-authoring.md](references/skill-authoring.md).
- **Agents** — `## Role`, `## Approach`, `## Workflow`. A persona plus the sequence it
  follows; name what it must not do.
- **Commands** — `## Trigger`, `## Parameters`, `## Behavior`. Numbered, deterministic.
- **Rules** — must / must-not bullets. One constraint per line, each independently
  checkable.
- **Contexts** — background knowledge and reference material, organised by topic.
- **Instructions** — folded into every configured target's context file (`CLAUDE.md` for
  claude, `AGENTS.md` for codex, `.cursor/rules/invariant-context.mdc` for cursor,
  `.github/copilot-instructions.md` for copilot, `CONVENTIONS.md` for aider) and read on
  every interaction, so every token is paid for repeatedly:
  1. Open with a **"This Package Contains"** table (item, type, installed as, when to
     use) and a partial-install note.
  2. Self-contained but concise — enough to act on the simple case alone.
  3. Reference every related skill explicitly, **by its installed name and path**.
  4. Example-driven, short fenced blocks.
  5. Action first, theory never.
  6. End with a `- [ ]` checklist.

Instruction template:

````markdown
<!-- package name: <package>  ->  slug: <slug> -->
# <Topic>

<What this covers.> For the full procedure, invoke the
[<slug>-<skill>](.claude/skills/<slug>-<skill>/SKILL.md) skill.

## This Package Contains

| Item | Type | Installed as | When to use |
|------|------|--------------|-------------|
| `<instruction>` | Instruction | folded into this context file | <short description> |
| `<skill>` | Skill | `<slug>-<skill>` | <short description> |
| `<agent>` | Agent | `<slug>-<agent>` | <short description> |

> **Partial installs:** Some items above may not be present in your
> `.claude` folder. Invariant lets users install only a subset of a
> package. Use what's available.

## <Section>

<Concise explanation + a short fenced example.>

## Checklist

- [ ] Validation point 1.
- [ ] Validation point 2.
````

Substitute the computed slug — never ship `<slug>` as a literal. An instruction is the
one item type whose *own* name is never prefixed (it has no path; it is folded into the
context file), which is exactly why it must spell everyone else's.

## Checklist

- [ ] Manifest is `invariant.json`; mode (project / package / hybrid) matches the intent.
- [ ] `name` lowercase + hyphens; `version` is semver.
- [ ] `items` was generated by the CLI, not hand-written; `active`/`packages` untouched by hand.
- [ ] `README.md` exists at the package root.
- [ ] Every skill is a folder containing `SKILL.md`; other items are `.md` files or folders of `.md`.
- [ ] Every `SKILL.md` opens with `name` + `description` frontmatter inside the published limits.
- [ ] Each skill's `name` matches its qualified installed name.
- [ ] Each skill body is under 500 lines, references one level deep, inputs / outputs / failures named.
- [ ] Installed names computed from the slug **before** any content was authored.
- [ ] Every cross-item reference spells the prefixed path; intra-skill links stay relative.
- [ ] `invariant.json` checked after `refresh` — no item description reads `---`.
- [ ] `invariant package validate` reports no drift and no `unprefixed_path_reference` warnings.
- [ ] `.agents/` and the target folders were never hand-edited or committed.
- [ ] Publish only on an explicit request, authenticated (`INVARIANT_TOKEN` / `invariant login`).
