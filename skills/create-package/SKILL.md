# Skill: Create Invariant Package — scaffold a publishable package, compute its installed names, validate and publish

Scaffold a new Invariant package — directory structure, item files, and a single `invariant.json` manifest — then let the CLI populate and validate it.

## Usage

Invoke when a user wants to author a new publishable Invariant package. Gather metadata, create the item files on disk, then drive the `invariant package` CLI to generate the manifest.

## Key facts

- One manifest file: **`invariant.json`**. (The older `invariant-package.json` no longer exists.)
- The same `invariant.json` schema powers three modes, auto-detected by content:
  - **Project** — consumes packages (`targets` / `packages` / `active`).
  - **Package** — publishable (`items` block present).
  - **Hybrid** — both.
- The `items` block is **auto-generated by scanning the package directory** — you never hand-write it. Create the files first; the CLI fills `items` in and extracts each item's description from the first non-empty line of its primary file.

## Installed names and paths

An item does not keep its bare name once installed. The CLI prefixes it with a slug of
the **package** name, so two packages shipping a `frontend` skill cannot overwrite each
other:

```
slug(packageName)  -> drop "@", "/"->"-", lowercase, non-[a-z0-9._-]->"-", collapse "-"
qualified(pkg, item) -> item if item === slug or item starts with slug + "-"
                        otherwise slug + "-" + item
```

`docs` + `frontend` → `docs-frontend`. `@invariant/skills` + `frontend` →
`invariant-skills-frontend`. The rule is a pure function — computable by hand before
publishing — and idempotent.

Where the installed name shows up:

| Location | Prefixed | Path |
|---|---|---|
| Canonical store | yes | `.agents/<type>/<qualified>` (folder) or `.agents/<type>/<qualified>.md` |
| Claude Code | yes | `.claude/<type>/<qualified>` — a symlink into `.agents/` |
| Cursor | yes | `.cursor/rules/<qualified>.mdc` |
| Copilot | yes | `.github/instructions/<qualified>.instructions.md` |
| Codex, Aider | inherited | read `.agents/` or embed the content |
| Contexts, instructions | **no** | `.invariant/{contexts,instructions}/<package>/<name>.md`, folded into each target's context file |
| Package cache | **no** | `.invariant/cache/<package>@<version>/<type>/<item>` |
| Your repository | **no** | keep authoring `skills/frontend/` — the prefix is an install-time projection |
| CLI arguments | **no** | `invariant add skill:<package>/<item>` takes the item's own name |

`.agents/` and every target folder are generated and gitignored — rebuilt by
`invariant sync`. Never author into them, never commit them.

Nothing rewrites content at install time: **any link to your own item must spell the
prefixed path yourself.** Full algorithm, both authoring strategies, collision rules and
the pre-prefix upgrade path: [package-naming.md](references/package-naming.md).

## The manifest (package mode)

```json
{
  "name": "clean-arch",
  "version": "1.2.0",
  "description": "Clean architecture rules and agents.",
  "author": "invariant-labs",
  "license": "MIT",
  "repository": "https://github.com/invariant-labs/clean-arch",
  "items": {
    "agents": [{ "name": "planner", "description": "Plans tasks by layer." }],
    "rules":  [{ "name": "layer-deps", "description": "Enforces dependency direction." }]
  }
}
```

| Field | Required | Notes |
|---|---|---|
| `name` | yes | lowercase, hyphens allowed; the `invariant install <name>` id |
| `version` | yes | semver `major.minor.patch` |
| `description` | recommended | shown in registry / search |
| `author` | no | name or handle |
| `license` | no | e.g. `MIT`, `Apache-2.0` |
| `repository` | no | source repo URL |
| `items` | auto | `type → [{name, description}]`. Presence marks the file a package. **Generated by `invariant package create` / `refresh` — do not hand-maintain.** |

## Item types (exactly six)

`agents`, `skills`, `commands`, `rules`, `contexts`, `instructions`.

- **Skills** — always a folder `skills/<name>/` with a required `SKILL.md`; extra `.md` files and sub-folders are bundled. Item name = folder name. A skill is never a single file.
- **All other types** — either a single file `<type>/<name>.md` (item name = filename without `.md`) or a folder `<type>/<name>/*.md` (item name = folder name; all `.md` bundled). Mix freely within a type.
- Only include directories for the types your package provides.

Example layout:

```
my-package/
├── invariant.json
├── agents/
│   ├── planner.md
│   └── reviewer/
│       ├── guidelines.md
│       └── checklist.md
├── skills/
│   └── test-writer/
│       ├── SKILL.md
│       └── templates/unit-test.md
├── rules/
│   └── layer-deps.md
├── contexts/
│   └── overview.md
└── instructions/
    └── onboarding.md
```

## Procedure

### Step 1 — Gather metadata

Ask for: package **name** (lowercase, hyphens), **description**, **author**, **license** (default `MIT`), **repository** (optional), initial **version** (default `1.0.0`).

### Step 2 — Choose items

Ask which of the six types are needed; for each item collect a **name** and a one-line **description**. The description should become the first heading/line of the item file — the CLI reads it back into the manifest.

Then, **before authoring any content**, compute the installed name of every item with
the rule above and write the map down:

```
package @acme/docs  ->  slug acme-docs
  skills/frontend        -> .claude/skills/acme-docs-frontend/SKILL.md
  agents/reviewer        -> .claude/agents/acme-docs-reviewer.md
  instructions/onboarding-> .invariant/instructions/@acme/docs/onboarding.md (not prefixed)
```

Links written from this map are right the first time; links patched afterwards are the
usual source of dead paths.

### Step 3 — Scaffold the files on disk

Create the package directory and, for each item:
- **Skill** → `skills/<name>/SKILL.md` (+ any support files).
- **Other** → `<type>/<name>.md` (single file) or `<type>/<name>/*.md` (folder).

Author each file's content (see guidelines below). **Do not hand-write the `items` block** — the CLI generates it next.

Author under the item's **own** name — `skills/frontend/`, not `skills/acme-docs-frontend/`
— unless you deliberately pre-prefix (safe by idempotence, and worth it when the slug is
short: repository layout then matches installed layout byte-for-byte, and a skill's
`name:` frontmatter matches its installed folder). Whichever you pick, apply it to every
item in the package.

### Step 4 — Generate the manifest

From the package root:

```bash
invariant package create \
  --name <name> --version <version> \
  --description "<desc>" --author "<author>" \
  --license MIT --repository "<url>"
```

This scans the folder, writes/updates `invariant.json`, and fills the `items` block (it runs a refresh internally). If `invariant.json` already exists it is updated in place and switched to Package (or Hybrid) mode.

> **Bootstrap gotcha (current CLI):** on a manifest that has no `items` block yet,
> `create` writes the metadata and then fails with
> `✖ This directory is not a publishable package. No 'items' block in invariant.json.`
> The metadata *was* written. Add an empty block by hand once —
> `"items": {}` — and run `invariant package refresh`; the scan then fills it in and
> every later `create` / `refresh` works normally.

After adding/removing item files later, re-sync the manifest:

```bash
invariant package refresh
```

### Step 5 — Validate

```bash
invariant package validate
```

Reports `missing_on_disk` (declared but file absent) and `undeclared_on_disk` (file present but not in manifest). Resolve drift — usually by running `invariant package refresh`.

It also warns `unprefixed_path_reference` when an item's content links to
`.claude/<type>/<name>` (or `.agents/`, `.cursor/rules/`, `.github/instructions/`) for
one of **your own** items without the prefix, naming the path that will actually exist.
Warnings are advisory — they never make a package invalid — but each one is a link that
404s after install. Fix them all.

To read the correct paths straight out of the CLI:

```bash
invariant inspect <package> --paths
```

Prints, tab-separated: package, item type, installed name, canonical path.

### Step 6 — Publish

```bash
invariant package publish
```

Validates, bundles (gzip tar of `invariant.json` + item files), and uploads to the registry. Requires authentication: set `INVARIANT_TOKEN`, or run `invariant login`.

## Content guidelines per type

- **Agents** — `## Role`, `## Approach`, `## Workflow`.
- **Skills** — `SKILL.md` with `## Usage` (when to invoke) + `## Procedure` (ordered `### Step N`).
- **Commands** — `## Trigger`, `## Parameters`, `## Behavior`.
- **Rules** — constraints as must / must-not bullet points.
- **Contexts** — background knowledge + reference material.
- **Instructions** — folded into every configured target's context file (`CLAUDE.md` for
  claude, `AGENTS.md` for codex, `.cursor/rules/invariant-context.mdc` for cursor,
  `.github/copilot-instructions.md` for copilot, `CONVENTIONS.md` for aider) and read on
  every interaction, so every token is paid for repeatedly:
  1. Open with a **"This Package Contains"** table (item, type, installed as, when to use) + a partial-install note.
  2. Self-contained but concise.
  3. Reference any related skill explicitly, **by its installed name and path**.
  4. Example-driven (short fenced blocks).
  5. Action-first.
  6. End with a `- [ ]` checklist.

Instruction template:

````markdown
<!-- package name: <package>  ->  slug: <slug> -->
# <Topic>

<What this covers.> For interactive guidance, invoke the
[<slug>-<skill>](.claude/skills/<slug>-<skill>/SKILL.md) skill.

## This Package Contains

| Item | Type | Installed as | When to use |
|------|------|--------------|-------------|
| `<instruction>` | Instruction | folded into this context file | <short description> |
| `<skill>` | Skill | `<slug>-<skill>` | <short description> |
| `<agent>` | Agent | `<slug>-<agent>` | <short description> |

> **Partial installs:** Some items above may not be present in your
> `.claude` folder. Invariant lets users install only a subset of a
> package. Use what's available.

## <Section>

<Concise explanation + a short fenced example.>

## Checklist

- [ ] Validation point 1.
- [ ] Validation point 2.
````

The `<slug>-` prefixes are literal in the generated file — substitute the computed slug,
do not leave a placeholder. An instruction is the one item type whose *own* name is never
prefixed (it has no path; it is folded into the context file), which is exactly why it
must spell everyone else's.

## Checklist

- [ ] Manifest is `invariant.json` (never `invariant-package.json`).
- [ ] `name` lowercase + hyphens; `version` is semver.
- [ ] `items` block was generated by the CLI (`package create` / `refresh`), not hand-written.
- [ ] Every skill is a folder containing `SKILL.md`.
- [ ] Other items are single `.md` files or folders of `.md` files.
- [ ] Installed names computed from the package slug **before** any content was authored.
- [ ] Every reference to one of the package's own items spells the prefixed path.
- [ ] `invariant package validate` reports no drift and no `unprefixed_path_reference` warnings.
- [ ] `.agents/` and the target folders were never hand-edited or committed — they are generated by `invariant sync`.
- [ ] Authenticated (`INVARIANT_TOKEN` / `invariant login`) before `invariant package publish`.
